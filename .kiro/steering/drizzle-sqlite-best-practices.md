# Drizzle + SQLite: Database Access Best Practices

Mandatory rules for all database access in InGen-SmartAI. Every developer and AI agent MUST follow these when reading, writing, or querying SQLite data.

## Golden Rule

**All SQLite access goes through Drizzle ORM. No exceptions.**

The only raw `sqlite` usage permitted is the bootstrap in `db/index.js` (opening the database, setting PRAGMAs, running migrations). Every other file uses the Drizzle `db` instance exclusively.

```
ALLOWED:
  db.select().from(issues).where(eq(issues.status, 'Open')).all()
  db.insert(emails).values({...}).onConflictDoUpdate({...}).run()
  db.delete(kvCache).where(like(kvCache.key, 'cache:%')).run()
  db.all(sql`SELECT ... complex query ...`)    ← Drizzle raw SQL escape hatch

PROHIBITED:
  sqlite.prepare('SELECT * FROM issues WHERE status = ?').all('Open')
  sqlite.prepare('INSERT INTO emails ...').run(...)
  dbRun('INSERT INTO ...', [...params])
  dbGet('SELECT ...', [...params])
```

## Architecture

### Single Database, Single Connection

```
data/{env}/smartai.db          ← one SQLite file per environment
    ↓
db/index.js                    ← singleton better-sqlite3 + Drizzle instance + migrations
db/kv.js                       ← kvGet/kvSet/kvDel convenience helpers
    ↓
db/schema.js                   ← Drizzle schema (single source of truth for table shapes)
    ↓
drizzle/                       ← migration SQL files (generated by drizzle-kit)
    ↓
domain modules                 ← import { db } from './db/index.js'
(issues-store, org-store,         import { issues, orgMembers, ... } from './db/schema.js'
 eng-metrics, local-store,        import { kvGet, kvSet } from './db/kv.js'
 insight-store, prompt-store,
 unified-cache, etc.)
```

### What Each File Owns

| File           | Responsibility                                                                          | Exports                                                     |
| -------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `db/index.js`  | Opens DB, sets PRAGMAs, runs Drizzle migrations, creates Drizzle instance               | `db`                                                        |
| `db/schema.js` | Drizzle table definitions — the single source of truth for all column types and indexes | All table objects (`issues`, `orgMembers`, `kvCache`, etc.) |
| `db/kv.js`     | Convenience wrappers for the `kv_cache` table (Drizzle-based)                           | `kvGet`, `kvSet`, `kvDel`                                   |
| `drizzle/`     | Migration SQL files generated by `npm run db:generate`                                  | Applied automatically on boot by `db/index.js`              |
| Domain modules | Business logic queries using `db` and schema tables                                     | Domain-specific functions                                   |

### Schema Changes Workflow

When adding or modifying a table:

1. Edit `db/schema.js` (the single source of truth)
2. Run `npm run db:generate` to create a migration file in `drizzle/`
3. Commit both the schema change and the migration file
4. On next boot, `db/index.js` applies the migration automatically

## Rules

### 1. Always Import `db`, Never `sqlite`

```js
// ✅ CORRECT — every domain module
import { db } from './db/index.js';
import { issues, issueActivities } from './db/schema.js';
import { eq, and, gt, desc, sql, count } from 'drizzle-orm';

// ❌ WRONG — no domain module should import sqlite
import { sqlite } from './db/connection.js';
```

The only file that touches `sqlite` directly is `db/index.js` (bootstrap). No other file imports it.

### 2. Use Drizzle Query Builder for Standard CRUD

For straightforward reads, writes, updates, and deletes — use the Drizzle query builder. It gives you type hints, autocompletion, and prevents SQL typos.

```js
// SELECT
const openIssues = db
  .select()
  .from(issues)
  .where(notInArray(issues.status, ['Resolved', 'Closed']))
  .orderBy(desc(issues.updatedAt))
  .all();

// INSERT with upsert
db.insert(engMetricsWeekly)
  .values({ alias, weekId, crsCreated: 5, fetchedAt: new Date().toISOString() })
  .onConflictDoUpdate({
    target: [engMetricsWeekly.alias, engMetricsWeekly.weekId],
    set: { crsCreated: 5, fetchedAt: new Date().toISOString() },
  })
  .run();

// UPDATE
db.update(insights)
  .set({ readAt: new Date().toISOString() })
  .where(eq(insights.id, insightId))
  .run();

// DELETE
db.delete(emails).run();

// COUNT
const { c } = db.select({ c: count() }).from(issues).get();
```

### 3. Use `sql` Template Literals for Complex Queries

When you need SQLite-specific functions (`julianday`, `strftime`, `GROUP_CONCAT`, `date('now', ...)`), use Drizzle's `sql` template literal. This gives you parameterized queries with full SQLite expression power.

```js
import { sql } from 'drizzle-orm';

// Computed columns
const rows = db
  .select({
    ...getTableColumns(issues),
    ageDays: sql < number > `CAST(julianday('now') - julianday(${issues.createdAt}) AS INTEGER)`,
  })
  .from(issues)
  .where(notInArray(issues.status, ['Resolved', 'Closed']))
  .orderBy(asc(issues.impact))
  .all();

// Date filtering with parameters
const recentActivities = db
  .select()
  .from(issueActivities)
  .where(gt(issueActivities.timestamp, sql`date('now', '-' || ${days} || ' days')`))
  .all();

// Prefix matching (use like() instead of SQLite GLOB — Drizzle has no glob() operator)
db.delete(kvCache).where(like(kvCache.key, 'cache:my-feature:%')).run();
```

### 4. Use `db.all(sql`...`)` for Truly Complex Queries

For multi-table JOINs with aggregations, subqueries, or SQLite-specific syntax that would be unreadable as query builder chains — use Drizzle's raw SQL escape hatch. This still gives you parameterization (no SQL injection) while keeping the query readable.

```js
// ✅ CORRECT — Drizzle raw SQL with parameterization
const summary = db.all(sql`
  SELECT
    ia.person,
    COUNT(DISTINCT ia.issueId) as issueCount,
    COUNT(*) as activityCount,
    MAX(ia.timestamp) as lastActiveAt,
    GROUP_CONCAT(DISTINCT ia.action) as actionTypes
  FROM issue_activities ia
  WHERE ia.timestamp > date('now', '-' || ${days} || ' days')
  GROUP BY ia.person
  ORDER BY activityCount DESC
`);

// ❌ WRONG — raw sqlite.prepare with string interpolation
const summary = sqlite.prepare(`...WHERE timestamp > date('now', '-' || ${days} || ' days')`).all();
```

Key difference: `sql` template literals parameterize `${days}` as a bound parameter. String interpolation in `sqlite.prepare()` injects the value directly into the SQL string.

### 5. Always Use Transactions for Bulk Writes

Any operation that writes multiple rows MUST be wrapped in a transaction. Without a transaction, each write auto-commits individually — this is 10-100x slower and risks partial writes on failure.

```js
// ✅ CORRECT — transaction for bulk operations
db.transaction((tx) => {
  tx.delete(emails).run();
  for (const e of emailList) {
    tx.insert(emails).values({
      id: e.id,
      subject: e.subject,
      date: e.date,
      data: JSON.stringify(e),
    }).run();
  }
  tx.insert(syncMeta)
    .values({ store: 'emails', updatedAt: now, count: emailList.length })
    .onConflictDoUpdate({ target: syncMeta.store, set: { updatedAt: now, count: emailList.length } })
    .run();
});

// ❌ WRONG — N individual auto-committed writes
for (const e of emailList) {
  db.insert(emails).values({...}).run();  // each one is a separate transaction
}
```

Rule of thumb: if you're writing more than 1 row, use a transaction.

### 6. Never String-Interpolate Values into SQL

This is the most important security and correctness rule. Always use parameterized queries.

```js
// ✅ CORRECT — parameterized
db.select()
  .from(issues)
  .where(gt(issues.updatedAt, sql`date('now', '-' || ${days} || ' days')`))
  .all();

// ❌ WRONG — string interpolation (defeats statement caching, risks injection)
const dateFilter = `AND updatedAt > date('now', '-' || ${days} || ' days')`;
sqlite.prepare(`SELECT * FROM issues WHERE 1=1 ${dateFilter}`).get();
```

Even when the value comes from internal code and isn't user input — always parameterize. It's a habit that prevents bugs when code gets refactored.

### 7. Schema Is the Single Source of Truth

`db/schema.js` defines every table, column, index, and constraint using Drizzle's `sqliteTable()`. Schema changes are applied to the database via Drizzle migrations.

When adding or modifying a table:

1. Edit `db/schema.js`
2. Run `npm run db:generate` to create a migration file
3. Commit both the schema change and the migration file
4. On next boot, `db/index.js` applies pending migrations automatically

```js
// schema.js — the single source of truth
export const myTable = sqliteTable(
  'my_table',
  {
    id: text('id').primaryKey(),
    name: text('name').notNull(),
    createdAt: text('created_at').notNull(),
  },
  (table) => [index('idx_my_table_name').on(table.name)]
);
```

### 8. Use `kvGet`/`kvSet` for Unstructured Key-Value Data

The `kv_cache` table is a general-purpose key-value store. Use the helpers from `db/kv.js` for simple get/set operations on JSON blobs that don't need their own table.

```js
import { kvGet, kvSet } from './db/kv.js';

// Good use cases for kv:
kvGet('agent-history'); // small JSON blob, no querying needed
kvSet('sync-email', { lastSyncTimestamp: '...' });
kvGet('ecd-history'); // historical snapshots, read as a whole

// Bad use cases for kv (should have their own table):
kvSet('all-emails', hugeArray); // structured data that needs querying → use emails table
```

When to use `kvGet`/`kvSet` vs. a dedicated table:

- **kv**: Data is always read/written as a whole blob, no need to query individual fields, small payload
- **Table**: Data has structure you need to query, filter, sort, join, or aggregate

### 9. One kv Key Per Concern

Never share a single kv key across multiple independent writers. This causes read-modify-write race conditions when writers run concurrently.

```js
// ✅ CORRECT — separate keys per concern
kvSet('sync-email', { lastSyncTimestamp: '...' });
kvSet('sync-slack', { lastSlackSyncTimestamp: '...' });
kvSet('sync-insights', { lastInsightRun: '...', insightsGenerated: 5 });

// ❌ WRONG — shared key with read-modify-write
const state = kvGet('sync_state') || {};
kvSet('sync_state', { ...state, lastSyncTimestamp: '...' });
// Another concurrent writer can overwrite your changes
```

### 10. Domain Modules Own Their Queries

Each domain module owns all queries for its tables. No cross-domain raw queries.

```
issues-store-db.js      → owns writes to issues, issue_activities, etc.
issues-store-queries.js → owns reads from issues, issue_activities, etc.
org-store.js            → owns all org_members, org_meta access
eng-metrics-*.js        → owns all eng_metrics_weekly, eng_bus_factor, etc.
local-store.js          → owns emails, calendar_events, slack_messages, sync_meta
insight-store.js        → owns insights table
prompt-store.js         → owns prompt_overrides table
unified-cache.js        → owns kv_cache entries with 'cache:' prefix
```

If you need data from another domain, call that domain's exported function — don't write a raw query against their tables.

```js
// ✅ CORRECT — call the domain module
import { getStats } from './issues-store.js';
const stats = getStats(30);

// ❌ WRONG — reaching into another domain's tables
import { db } from './db/connection.js';
import { issues } from './db/schema.js';
const count = db.select({ c: count() }).from(issues).get();
```

### 11. Read from SQLite, Not JSON Files

All data that has been migrated to SQLite MUST be read from SQLite. Never read stale JSON files when the data lives in a SQLite table.

```js
// ✅ CORRECT — read from the SQLite-backed store
import { getEmails, getCalendar, getSlackMessages } from './local-store.js';
const emails = getEmails().data;
const calendar = getCalendar().data;
const slack = getSlackMessages().data;

// ❌ WRONG — reading legacy JSON files
const raw = JSON.parse(fs.readFileSync(path.join(getDataDir(), 'emails.json'), 'utf8'));
const emails = raw.data;
```

This applies to: emails, calendar events, slack messages, issues, org data, eng metrics, insights, prompts, and all cached data. If it's in SQLite, read it from SQLite.

### 12. Synchronous by Default

`better-sqlite3` is synchronous. Drizzle on `better-sqlite3` is synchronous. Do not use `await` on Drizzle calls — it works (awaiting a non-Promise resolves immediately) but is misleading.

```js
// ✅ CORRECT — synchronous, no await
const rows = db.select().from(issues).all();
db.insert(issues).values({...}).run();

// ❌ WRONG — unnecessary await suggests async I/O
const rows = await db.select().from(issues).all();
await db.insert(issues).values({...}).run();
```

The only exception is if you're inside an `async` function and the surrounding code is async for other reasons (e.g., MCP calls). Even then, don't add `await` to the Drizzle calls themselves.

### 13. Use `.run()` for Writes, `.all()` for Multi-Row Reads, `.get()` for Single-Row Reads

Drizzle's `better-sqlite3` driver exposes three execution methods:

```js
db.insert(issues).values({...}).run();     // writes — returns { changes, lastInsertRowid }
db.select().from(issues).all();            // multi-row reads — returns array
db.select().from(issues).where(...).get(); // single-row reads — returns object or undefined
```

Never use `.all()` when you expect one row (wasteful), and never use `.get()` when you expect multiple rows (silently drops data).

### 14. Connection Configuration

The database connection in `db/index.js` sets these PRAGMAs. Do not change them without understanding the implications:

```js
sqlite.pragma('journal_mode = WAL'); // Write-Ahead Logging — concurrent reads during writes
sqlite.pragma('busy_timeout = 5000'); // Wait up to 5s for locks instead of failing immediately
sqlite.pragma('foreign_keys = ON'); // Enforce foreign key constraints
```

These are set once at connection time and apply to all queries. Do not set PRAGMAs in domain modules.

### 15. Unified Cache Uses `kv_cache` with Namespaced Keys

The unified cache system (`unified-cache.js`) stores cache entries in the `kv_cache` table with keys prefixed by `cache:{name}:`. This is an implementation detail — consumers use `createCache()` and never touch `kv_cache` directly.

```js
// ✅ CORRECT — use the cache abstraction
import { createCache } from './unified-cache.js';
const myCache = createCache({ name: 'my-feature', tier: 'sqlite', ttl: TTL_1_HOUR });
myCache.set('key', value);
const result = myCache.get('key');

// ❌ WRONG — bypassing the cache to write directly to kv_cache
import { kvSet } from './db/connection.js';
kvSet('cache:my-feature:key', { value, cachedAt: Date.now() });
```

### 16. Test Database Isolation

Tests use `:memory:` SQLite databases (configured in `db/index.js` when `NODE_ENV=test`). This means:

- Each test run gets a fresh database
- No test data persists between runs
- Tests can run in parallel without conflicts
- The same DDL and schema apply to test databases

Do not create separate test database files or skip database setup in tests.

## Anti-Patterns to Avoid

| Anti-Pattern                                    | Why It's Bad                                      | Do This Instead                                          |
| ----------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------- |
| `sqlite.prepare('SELECT...')` in domain modules | Bypasses Drizzle, inconsistent access             | Use `db.select()` or `db.all(sql\`...\`)`                |
| `await dbRun('INSERT...')`                      | Fake async, misleading, no type safety            | Use `db.insert(table).values({...}).run()`               |
| String interpolation in SQL                     | Defeats parameterization, breaks statement cache  | Use `sql` template literals or `?` params                |
| Bulk writes without transaction                 | 10-100x slower, risks partial writes              | Wrap in `db.transaction((tx) => {...})`                  |
| Shared kv key across concurrent writers         | Read-modify-write race condition                  | One key per concern                                      |
| Reading JSON files for data in SQLite           | Stale data, inconsistent with SQLite source       | Use domain module getters                                |
| `import { sqlite }` in domain modules           | Direct DB access bypasses Drizzle                 | Import `db` only                                         |
| Prepared statements inside loops                | Recompiles SQL on every iteration                 | Hoist to module scope or use Drizzle                     |
| `new Date().toISOString()` scattered everywhere | Inconsistent timestamp format                     | Use ISO strings consistently, compute once per operation |
| Cross-domain raw queries                        | Breaks encapsulation, creates hidden dependencies | Call the domain module's exported function               |

## Quick Reference: Drizzle Imports

```js
// Connection, schema, and kv helpers
import { db } from './db/index.js';
import { kvGet, kvSet, kvDel } from './db/kv.js';
import { issues, orgMembers, engMetricsWeekly /* etc */ } from './db/schema.js';

// Drizzle operators (import what you need)
import {
  eq, // equality: eq(issues.id, 'abc')
  and, // AND: and(eq(...), gt(...))
  or, // OR: or(eq(...), eq(...))
  gt, // greater than: gt(issues.updatedAt, cutoff)
  gte, // greater than or equal
  lt, // less than
  lte, // less than or equal
  isNull, // IS NULL: isNull(insights.readAt)
  isNotNull, // IS NOT NULL
  notInArray, // NOT IN: notInArray(issues.status, ['Resolved', 'Closed'])
  inArray, // IN: inArray(issues.type, ['taskei', 'sim'])
  like, // LIKE: like(kvCache.key, 'cache:%')
  asc, // ORDER BY ASC
  desc, // ORDER BY DESC
  sql, // raw SQL template: sql`julianday('now')`
  count, // COUNT(*): count()
  avg, // AVG: avg(insights.confidence)
  sum, // SUM: sum(engMetricsWeekly.crsCreated)
  getTableColumns, // spread all columns: { ...getTableColumns(issues) }
} from 'drizzle-orm';
```
